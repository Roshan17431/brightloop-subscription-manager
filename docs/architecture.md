# Brightloop architecture

## Scope and source
The supplied Subscription_Management_System.pdf is preserved here as the business specification. phase-1-requirements.md preserves the expanded implementation scope. Phase 1 builds identity, customers, products/variants, plan definitions and subscription lifecycle. Phase 2 adds recurring billing execution, invoice generation and lifecycle, PDF/email delivery, and automatic tax and discount engines. Phase 3 adds recorded payment management, partial/multiple payment reconciliation, overdue invoice tracking, subscription pause/resume/renewal/early-closing operations, and reusable quotation templates with quotation-to-subscription conversion. Phase 4 adds PostgreSQL-backed executive financial analytics (MRR/ARR normalization, revenue/payment trends, overdue aging buckets, CSV reporting) and the customer self-service portal.

## Runtime
Next.js App Router serves the UI; a same-origin /api/v1 proxy forwards requests to Spring Web MVC. TanStack Query owns server state, React Hook Form/Zod validate forms, and the server remains authoritative. Java 21 and Spring Boot 4 run a modular monolith using PostgreSQL and Flyway. Hibernate validates the migrated schema. Local Compose runs PostgreSQL and Mailpit; application processes run locally for fast development.

## Boundaries
com.brightloop.modules contains auth, user, customer, product, plan, subscription, quotation, tax, discount, invoice, payment, billing, analytics and audit features. Constructor-injected services enforce transactions and domain validation. Controllers return DTO envelopes. Foreign keys and unique constraints protect relationships against races. Catalog, tax, discount, and manual billing execution writes are admin-only; staff and admins manage day-to-day customers, subscriptions, lifecycle operations, quotation templates, quotations, invoice confirmations/cancellations/emails, payment recording/reversals, and executive analytics/reports. Customers see only their own subscriptions, quotations, invoices, payments, and customer portal overview, and can self-service pause/resume/renew/close their own subscriptions when plan rules allow.

## Identity
Persistent server-side sessions use HttpOnly cookies and CSRF protection. No browser localStorage tokens. Reset tokens are cryptographically random, stored hashed, expire, and can be consumed once. SMTP delivers links; Mailpit is development delivery only. Initial admin provisioning requires explicit environment variables, never a seeded password. Role mutations are admin-only and audited.

## Financial and lifecycle decisions
BigDecimal stores money. Financial DTOs serialize decimal strings and the UI formats with integer cents to avoid loss of precision for large totals. Internal cost prices are redacted from customer catalog views. Subscription lines snapshot the product base sales price plus selected variant adjustment; the underlying product price is unchanged. Explicit tax-rate snapshots support line totals only, not a tax-rules engine. Plan prices remain definition metadata, not simulated billing. Lifecycle transitions are validated and concurrent edits protected. Availability and quantity are checked when drafts are created/edited; plan definitions remain separate from customer subscriptions.

## Operational choices
Bounded pagination and search, database constraints/indexes and explicit fetch plans support normal list/detail use. Audit records participate in mutation transactions and never include credentials. Readiness and health use Actuator. Security headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`), `HttpOnly`/`SameSite=Lax` session cookies, CSRF validation, SQL wildcard backslash escaping, and CSV formula injection neutralization are enforced across `/api/v1`. Performance under 3,000+ subscriptions, 3,000+ invoices, and 2,000+ payments is verified in `Phase5SecurityFinancialPerformanceIntegrationTest` (p95 <= 51.34 ms single-user and p95 = 378.23 ms under 20 concurrent VUs, well within the 2,000 ms SLA).
